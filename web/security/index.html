2. Non-Custodial Signing Architecture

  • Read-only scan: Step 1 queries balances, code (eth_getCode), and allowances using only the public address.
  • Local signing only: Step 3 signs the EIP-7702 authorization and EIP-712 rescue intent in memory inside the browser tab using only the private key of the already compromised wallet.
  • No key transmission or custody: The private key is never sent to UNSWEEP servers; only signatures are submitted to the relayer, which sponsors gas and submits the type-4 transaction transferring tokens directly to your safe address.
  • Self-verification: Inspect the signing code in the repository, check DevTools → Network before signing, and compare served app.js SHA-256 against the repository commit.

3. What UNSWEEP Never Asks For

  • Never your 12/24-word seed phrase or recovery phrase.
  • Never the private key of your new safe destination wallet.
  • Never upfront payments, deposits, or ETH sent to the compromised wallet.
  • UNSWEEP never sends unsolicited direct messages (DMs) on Telegram, Discord, X, or Reddit.

4. Unaudited Risks & Known Limitations

  • No third-party audit yet: Smart contracts, browser signing logic, and relayer infrastructure have not been certified by an independent security firm or penetration test.
  • Execution & front-running risk: A sweeper bot or competing actor may still race transactions or drain assets if a wallet is actively monitored.
  • Scope limits: Only supported ERC-20 tokens on Base (16) and Arbitrum One (12) are in primary scope; unverified ERC-20s have no guarantee, NFTs are unsupported, and funds already stolen cannot be recovered.
  • Full scope details: See UNSWEEP_RECOVERY_SCOPE.md and docs/SECURITY_EVIDENCE.md.
